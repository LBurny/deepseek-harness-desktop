This release fixes the two file card menu entries that opened nothing: "Show in File Explorer" and "Open containing folder" now really raise an Explorer window with your file selected. The cause was upstream rather than in the shell, and it hit every dsh running on Windows, so the shell now carries a signature-gated patch for it. Nothing else changes: a normal in-place update is enough, and your sessions, MCP servers, skills and choices are untouched.

### 1. What was wrong

The reveal was running all along. dsh's shared native command runner spawns every host command with windowsHide enabled, which on Windows means SW_HIDE is set on the child process, and an Explorer folder window follows SW_SHOWDEFAULT: it inherits that hidden state. The window was built at the right folder with the right file already selected, but it was created invisible. Because the host route still answered 204, the card showed "requested" while the desktop stayed empty, which is exactly the "clicking did nothing" symptom.

Two pieces of evidence, both from the machine that reported it. Its desktop already held four invisible Explorer windows at the delivered file's folder, each with the correct file selected, so the click had reached the OS all along and only visibility was lost. And a single variable experiment through the real production module flipped the same call from IsWindowVisible=false (windowsHide on) to true (windowsHide off). Upstream has not fixed it: the newest alpha published on npm still carries that same line, so a runtime bump cannot help.

### 2. The fix

A fifth in-place runtime patch, revealshow.rs, in the same shape as the four that came before it (signature gated, marker idempotent, atomic write, stops on drift). It exempts only explorer.exe from that option: windowsHide becomes false for it and stays true for every other command. The exemption is narrow on purpose. The powershell path behind "Open with default app" was measured visible even with windowsHide on, because it hands the request to the already running desktop explorer through ShellExecute, while console applications must keep their console hidden: the shell never flashes a console window and that rule stays intact. A PE header check confirms the split is safe: explorer.exe is a GUI subsystem binary (2), so it can never create a console in the first place, whereas powershell.exe and taskkill.exe are console binaries (3).

### 3. Verification

The full Rust suite passes (305 tests, 0 failures), including the upstream contract suite that runs against the real runtime and now also guards this patch's signature. The end-to-end check imported the module the real Rust patch had rewritten and called the very function the menu uses: the pristine copy produced an invisible window, the patched copy a visible one with the right file selected. The runtime inside the installer is untouched on disk; the patch is applied at startup and reapplied whenever a dsh self-update restores the file.

### 4. Compatibility

No runtime version change, no session format change, no configuration change. Updating in place is enough.
